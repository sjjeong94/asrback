## Whisper (`src/asrback/models/whisper.py`)

### 1. Continuous batching

- **현재**: `_decode_batch`는 배치의 모든 행이 EOS에 닿을 때까지 스텝을 반복합니다. 짧게 끝난 행도
  가장 긴 행이 끝날 때까지 패딩으로 계산되고, 그동안 새로 들어온 요청은 큐에서 기다립니다.
- **영향**: 출력 길이가 제각각인 실제 트래픽에서 처리량과 지연이 함께 나빠집니다.
  `--sort-by-length` 벤치마크는 출력 길이가 비슷하게 묶여서 이 손실이 잘 드러나지 않습니다.
- **개선**: 스텝 사이에 끝난 행 자리에 새 작업을 넣습니다. 그러려면 다음이 필요합니다.
  - 행마다 position을 따로 둡니다. 지금은 `_DecodeState.position`이 `(1,)` 하나뿐입니다.
  - 행마다 KV 마스크를 둡니다.
  - 새로 들어온 행의 인코더 출력과 prefix pass를 처리합니다.
  - 행별 position을 입력으로 받도록 CUDA graph 캡처를 다시 구성합니다.
- **측정**: 정렬하지 않은 동시 요청 부하에서 처리량과 p50/p99 지연을 측정합니다.

### 2. prefix 길이별 배치 분할

- **현재**: `_serve`가 작업을 `(prefix_length, limit)`별로 묶어 그룹마다 따로 디코딩합니다.
  긴 오디오는 두 번째 윈도우부터 이전 텍스트를 prefix로 붙이는데, 그 길이가 요청마다 다릅니다.
  그래서 동시에 들어온 윈도우들이 작은 그룹으로 쪼개져 순서대로 처리됩니다.
- **영향**: 히스토리는 `max_target_positions // 2 - 1`(223토큰)에서 잘리므로, 보통 2~3번째 윈도우
  이후에는 길이가 같아져 다시 묶입니다. 짧은 클립만 다루는 LibriSpeech에서는 이 문제가 생기지 않습니다.
- **개선**: prefix를 왼쪽으로 패딩하고, 행마다 위치 오프셋과 패딩 마스크를 둡니다. 1번을 구현하면 이 문제도
  함께 풀립니다.

### 1·2번 결과

- **사전 측정** (whisper-small, 같은 프로세스에서 128 스레드로 직접 호출):

  | 조건 | 전체 | 인코더 | 디코더 | 쓸모 있는 행-스텝 | 배치당 행 수 |
  | --- | --- | --- | --- | --- | --- |
  | LibriSpeech, 길이순 | 59.9 s | 27.5 s | 32.1 s | 77% | 15.2 |
  | LibriSpeech, 무작위 순서 | 84.3 s | 27.7 s | 56.2 s | 41% | 15.2 |
  | 긴 오디오, 조건화 켬 | 65.9 s | 8.0 s | 57.8 s | 65% | 2.8 (prefix 길이별로 5.3개 그룹) |
  | 긴 오디오, 조건화 끔 | 37.5 s | 7.6 s | 29.8 s | 60% | 15.4 |

  인코더는 배치 크기와 상관없이 윈도우당 약 10 ms로 이미 연산이 꽉 차 있어, 작은 묶음으로 자주 받아도 손해가 없습니다.
- **구현**: `max_batch_size`개 행의 풀을 두고, 4스텝마다 끝난 행의 결과를 돌려주고 큐의 새 윈도우를 빈 행에 넣습니다.
  새 윈도우는 staging 캐시에서 인코딩, 언어 감지, prompt pass, 첫 토큰 선택을 마친 뒤 KV와 상태를 풀의 빈 행으로
  복사합니다. prompt pass만 prefix 길이별로 따로 하고, 디코딩 스텝은 행마다 다른 위치(`scatter_`로 KV 쓰기,
  `(B,1,1,L)` 마스크)로 함께 돕니다.
- **정확성**: float32에서 직전 코드와 273건(언어 감지, prompt, `max_new_tokens`, translate, 조건화된 긴 오디오 포함)의
  토큰과 점수가 CUDA graph 경로에서 모두 같았습니다(eager 경로는 1건에서 점수 반올림만 차이).
- **결과** (whisper-small):

  | 조건 | 직전 코드 | continuous batching |
  | --- | --- | --- |
  | 직접 호출, LibriSpeech 무작위 순서 | 85.1 s | 62.2~63.1 s (-26%) |
  | 직접 호출, 긴 오디오 조건화 켬 | 63.2 s | 32.8~33.8 s (-47%) |
  | 직접 호출, 긴 오디오 조건화 끔 | 35.9 s | 29.1~30.8 s (-17%) |
  | 직접 호출, LibriSpeech 길이순 | 60.8 s | 59.7~63.0 s (변화 없음) |
  | 서버 + `asrback-eval`, ID 순서 | 81.2 s | 61.6 s (-24%) |
  | 서버 + `asrback-eval`, 길이순 (3회) | 60.2~60.9 s | 60.8~62.1 s (+1%, 노이즈 수준) |

  WER은 모든 조건에서 bf16 오차 범위 안이었습니다.
- **길이순이 개선되지 않는 이유**: 디코딩 스텝 시간은 32 s → 21 s로 줄지만, 새 윈도우를 받을 때마다 prompt pass
  (약 5 ms, eager라 커널 실행 비용이 지배)와 staging→풀 복사(윈도우당 0.3 ms)가 들고, 받는 횟수가 기존 배치 수의
  약 5배(배치당 2.9개)라 이득이 상쇄됩니다.
- **시도했다가 되돌린 것**: 빈 행이 풀의 1/4~1/2 생길 때까지 기다렸다 받기, prompt pass CUDA graph, 작은 텐서의
  pinned 비동기 복사. 계측상 준비 비용은 줄었지만 전체 시간은 노이즈 범위였습니다. 계측 없이 실행하면 커널 실행
  비용이 앞서 쌓인 인코더 작업(윈도우당 10 ms)에 가려지기 때문으로 보입니다.

### 3. 이전 텍스트 조건화를 끄는 옵션

- **현재**: `transcribe`는 윈도우마다 앞 윈도우 결과를 기다린 뒤 다음 윈도우를 큐에 넣습니다.
  그래서 요청이 하나뿐이면 긴 파일도 배치 크기 1로 처리됩니다.
- **개선**: openai-whisper의 `condition_on_previous_text=False`에 해당하는 옵션을 추가합니다. 옵션이 켜지면
  SenseVoice처럼 모든 윈도우를 한꺼번에 큐에 넣어 배치로 처리합니다.
- **고려사항**: 조건화를 끄면 윈도우 경계에서 문맥이 끊겨 WER이 달라질 수 있으니 정확도도 함께 비교합니다.

### 4. q/k/v projection 융합

- **현재**: `MultiHeadAttention`은 q, k, v를 서로 다른 GEMM 세 번으로 계산합니다.
- **개선**: 로드할 때 가중치를 하나로 이어 붙여 self-attention은 GEMM 한 번, cross-attention은 kv GEMM 한 번으로
  줄입니다. `k_proj`에는 bias가 없으므로 0 bias를 채웁니다.
- **영향**: 인코더와 eager 디코딩에서 조금 이득이 있습니다. CUDA graph 경로는 커널 실행 오버헤드가 이미 숨겨져
  있어서 이득이 더 작습니다.

### 5. mel 계산과 디코딩 겹치기

- **현재**: `_windows`는 디코딩을 시작하기 전에 모든 윈도우의 log-mel을 한꺼번에 계산합니다.
- **개선**: generator로 바꿔 한 윈도우를 디코딩하는 동안 다음 mel을 준비합니다. 첫 결과까지의 시간이 짧아지고
  메모리도 덜 씁니다.

## SenseVoice (`src/asrback/models/sensevoice.py`)

### 6. CTC logits 청크 처리

- **현재**: `ctc_lo`가 `(batch, frames, vocab)` 크기의 logits를 한 번에 만듭니다. B=32에 30초 윈도우
  (약 504프레임), vocab 약 2.5만이면 bf16으로 약 0.8GB입니다. `greedy_ctc`의 `logsumexp` 중간 텐서까지
  더하면 최대 1.6GB 정도까지 올라갈 수 있습니다.
- **개선**: `ctc_lo`부터 `greedy_ctc`까지를 배치(또는 시간 축) 단위로 나눠 계산합니다.
- **영향**: 속도는 거의 그대로이고, 아낀 메모리만큼 `max_batch_size`를 키울 수 있습니다.
- **측정**: `torch.cuda.max_memory_allocated()`로 최대 메모리를 비교하고, 배치 크기를 바꿔 가며 처리 시간을
  측정합니다.

### 7. 인코더 `torch.compile` 옵션

- **현재**: 인코더는 50층이고, 층마다 FSMN 부분에서 transpose → pad → depthwise conv → transpose를 거칩니다.
  이 과정에서 contiguous 복사가 생기고 LayerNorm과 elementwise 연산도 따로따로 실행됩니다.
- **개선**: Whisper의 `--compile-encoder`처럼 옵션을 추가합니다. 입력 길이가 가변이므로 프레임 수를 몇 개
  버킷으로 패딩한 뒤 `dynamic=False`로 버킷마다 미리 compile합니다. 어차피 마스크를 쓰고 있으니 패딩을
  더해도 결과는 같습니다.
- **고려사항**: (배치 버킷 × 길이 버킷)마다 compile하므로 시작 시간이 늘어납니다. 버킷 수를 적게 유지합니다.

### 8. 마스크 있는 배치의 attention 개선 (처음 제목: 마스크 없는 배치 늘리기)

- **현재**: 배치에 길이가 다른 행이 있으면 bool 마스크가 들어가서 SDPA가 flash 대신 efficient 커널을 고르고,
  FSMN 부분에도 마스크 곱셈이 더해집니다.
- **측정**: B=32, T=500(약 30초)에서 인코더 시간이 마스크 없이 301.5 ms, 마스크가 있으면 358.7 ms로 약 19% 느립니다.
  `--compile-encoder`를 켜도 279.6 ms 대 332.7 ms로 차이가 비슷합니다. 처음 예상보다 영향이 큽니다.
- **개선 후보**:
  - 길이가 정확히 같은 작업끼리 우선 묶어 마스크 없는 배치가 더 자주 나오게 합니다. 긴 오디오는 30초 윈도우가
    모두 같은 길이이므로 효과가 큽니다.
  - 마스크를 SDPA가 더 빠른 커널을 고를 수 있는 형태(예: additive float 마스크)로 바꿔 보고, 어느 부분
    (attention인지 FSMN 마스크 곱셈인지)이 느려지는지 먼저 프로파일링합니다.
- **고려사항**: 같은 길이만 기다리면 배치가 작아질 수 있으니, `take_similar`의 패딩 허용 폭과 함께 조정합니다.
- **원인 확인**: 느려지는 부분은 attention이었습니다. B=32, T=504에서 attention 한 번이 마스크 없이 0.457 ms(flash),
  bool 마스크로 1.189 ms(efficient)입니다. 레이어 70개를 합치면 마스크 유무에 따른 인코더 시간 차이의 대부분입니다.
  additive 마스크도 1.196 ms로 같았습니다.
- **시도 1 — cuDNN attention 우선**: 마스크가 있어도 0.494 ms로 빠르고 정확도도 같았습니다. 하지만 처음 보는 shape마다
  실행 계획을 만드는 데 약 36 ms가 걸려, 길이가 계속 바뀌는 LibriSpeech에서는 전체가 10.4~10.6초에서 13.8~15.7초로
  오히려 느려졌습니다. 채택하지 않았습니다.
- **시도 2 — varlen attention (채택)**: 마스크가 있으면 `torch.nn.attention.varlen.varlen_attn`(flash)을 씁니다.
  패딩된 배치를 `(B·T, H, D)`로 펼치고 `seqused_k`로 각 행의 key를 실제 길이에서 끊으므로, 프레임을 모으거나
  되돌리는 복사가 없습니다. 같은 배치 구성을 그대로 쓰므로 길이별 묶음을 바꿀 필요도 없었습니다.
  - attention 한 번 0.389 ms, fp64 기준 대비 최대 오차 0.0019(efficient 0.0020), 새 길이에 추가 비용 없음.
  - 인코더(마스크 배치): eager 5~10%, compile 6~17% 빠름. 마스크 없는 배치는 기존 flash 경로를 그대로 씁니다.
  - CUDA·bfloat16에서 시작할 때 동작을 확인하고, CPU나 float32에서는 기존 SDPA 경로를 씁니다.
- **결과** (LibriSpeech test-clean, `asrback-eval` 4 프로세스, 서버당 4회 중 2~4회 평균, 두 라운드):

  | | 수정 전 | 수정 후 |
  | --- | --- | --- |
  | eager | 10.18 s | 9.82 s (-3.5%) |
  | `--compile-encoder` | 9.20 s | 8.95 s (-2.7%) |

  - WER은 3.43~3.46%로 bf16 오차 범위 안입니다. 긴 오디오는 30초 윈도우가 대부분 같은 길이라(마스크 없음) 변화가
    없습니다.
  - 인코더의 개선폭보다 작은 것은 CTC, 후처리, HTTP와 GPU 유휴 시간(약 23%)이 전체 시간에 섞여 있기 때문입니다.

## 공통

### 9. pinned memory로 H2D 복사

- `_encode`(Whisper)와 `_decode_batch`(SenseVoice)는 일반 메모리에서 GPU로 복사합니다. pinned buffer와
  `non_blocking=True`를 쓰면 복사 시간이 조금 줄어듭니다. 복사량이 작아서 우선순위는 낮습니다.
- 서버 코드(`server.py`, `gather_batch`)에는 눈에 띄는 병목이 없습니다.

### 10. 이벤트 루프와 GPU 워커의 GIL 경합 해소

- **측정**: SenseVoice로 LibriSpeech test-clean을 평가하는 동안 GPU 사용률이 평균 52~58%였습니다. 그래서 7번
  (`--compile-encoder`)으로 인코더가 약 7% 빨라져도 전체 시간은 노이즈 범위 안에서만 달라졌습니다(12.9~13.8초 대
  12.4~13.0초).
- **asrfront는 병목이 아님**: LibriSpeech 전체(2620개 파일, 5.4시간) 기준 단일 스레드 비용입니다. 16 스레드에서
  5.5~8배로 확장되어 GIL도 제대로 놓습니다. 서버에서는 합쳐서 1초 미만이므로 asrfront 수정은 필요 없습니다.

  | 함수 | 단일 스레드 합계 | 파일당 | 16 스레드 |
  | --- | --- | --- | --- |
  | `load` (FLAC 디코딩) | 2.66 s | 1.0 ms | 0.34 s (7.9배) |
  | `sensevoice.fbank` | 1.32 s | 0.5 ms | 0.24 s (5.6배) |
  | `whisper.log_mel` | 1.81 s | 0.7 ms | 0.30 s (6.1배) |

- **원인** (py-spy로 서버 프로파일링, `--gil`과 `--idle` 각각):

  | 스레드 | GIL 점유 비율 | 주요 작업 |
  | --- | --- | --- |
  | 메인(asyncio 이벤트 루프) | 83% | uvicorn/Starlette 요청 처리, multipart 폼 파싱(`_get_form`) 23% |
  | GPU 워커 | 16% | PyTorch 커널 실행(eager 모드라 레이어마다 Python 호출) |
  | 요청 스레드 풀 | 1% | asrfront 호출 등 |

  - `python-multipart`는 순수 Python이고 이벤트 루프 스레드에서 돌아갑니다.
  - 워커는 커널을 실행할 때 GIL이 필요한데, 이벤트 루프가 GIL을 오래 잡고 있으면 기다려야 하고 그동안 GPU가 쉽니다.
  - 워커의 시간 분포: 모델 실행 약 65%, 작업 대기(`gather_batch`) 15%, 패딩 배열 복사 약 10%,
    GPU 동기화(`.tolist()`) 약 8%.
  - 한계: py-spy 오버헤드로 프로파일링 중 실행 시간이 13초에서 30초로 늘어서 비율은 대략적입니다. 평가 클라이언트도
    같은 머신에서 돌았지만, 코어가 16개라 문제는 코어 수보다 서버 프로세스 하나 안의 GIL입니다.
- **개선 후보**:
  1. **GPU 워커를 별도 프로세스로 분리**: HTTP 처리와 GIL을 나눠 쓰지 않게 됩니다. 특징은 shared memory로 넘기고,
     결과는 pipe나 queue로 돌려받습니다. 효과는 가장 확실하지만 구조 변경이 큽니다.
  2. **워커의 Python 호출 줄이기**: CUDA graph나 compile로 커널 실행 횟수를 줄여 워커가 GIL을 덜 필요로 하게
     합니다. 7번의 compile도 이 방향이지만 효과가 작았습니다. 길이 버킷을 둔 CUDA graph는 8번과 함께 검토합니다.
  3. **multipart 파싱 부담 줄이기**: 예를 들어 raw body 업로드를 지원합니다. OpenAI API 호환이 깨지므로 별도
     엔드포인트로만 가능합니다.
  4. **워커의 패딩 복사 줄이기**: 작은 개선으로, 요청 스레드에서 미리 만든 버퍼에 쓰거나 GPU에서 패딩합니다.
- **측정 방법**: 클라이언트를 다른 머신에서 돌리거나 CPU 코어를 나눠(`taskset`) 서버만의 처리량을 측정하고, GPU
  사용률과 함께 비교합니다.
- **결과** (`0c7f760`): 1번 후보(GPU 워커 프로세스 분리)를 `--model-process`로 구현하고 기본값으로 켰습니다.
  - 상한 확인: HTTP 없이 같은 프로세스에서 128개 스레드로 `transcribe()`를 직접 호출하면 SenseVoice 9.2초
    (GPU 79%), whisper-small 60.6초(GPU 95%)입니다.
  - 가벼운 다중 프로세스 클라이언트(httpx)로 LibriSpeech test-clean을 측정했습니다.

    | | 서버 프로세스 안 | `--model-process` |
    | --- | --- | --- |
    | SenseVoice | 11.1~11.5 s, GPU 64% | 9.4~9.5 s, GPU 77% |
    | whisper-small | 60.8 s, GPU 93% | 59.3 s, GPU 96% |

  - SenseVoice는 상한에 거의 닿았고, Whisper는 원래 GPU가 병목이라 차이가 없습니다.
  - 모델 프로세스가 죽으면 요청은 500, `/health`는 503을 돌려줍니다.
  - 처음 `asrback-eval`로 쟀을 때는 두 설정 모두 13~15초로 차이가 보이지 않았습니다. 평가 클라이언트가 먼저 한계에
    걸려 있었기 때문입니다(11번).

### 11. `asrback-eval` 클라이언트 병목 해소

- **현재였던 것**: `asrback-eval`은 한 프로세스에서 128개 스레드로 openai SDK를 호출했습니다. SDK가 요청마다 CPU를
  꽤 써서(pydantic 등) 18초 동안 CPU 24초를 쓰며 GIL에 묶였고, 서버보다 먼저 한계(약 13초)에 걸렸습니다.
  그래서 서버 쪽 개선이 측정에 드러나지 않았습니다.
- **개선**: `--processes`개(기본 4) 클라이언트 프로세스가 작업 큐에서 파일을 꺼내 요청을 보내고, 메인 프로세스는
  결과를 받는 대로 채점합니다. 시간 측정은 클라이언트 프로세스가 openai를 import하고 준비를 마친 뒤 시작합니다.
- **결과** (SenseVoice, `--model-process`, `--sort-by-length`):

  | `--processes` | 1 | 2 | 4 | 8 |
  | --- | --- | --- | --- | --- |
  | 시간 | 13.5 s | 10.6 s | 10.5 s | 10.8 s |

  - 같은 순서(긴 파일부터)로 보낸 가벼운 클라이언트는 10.3초여서, 이제 클라이언트 오버헤드는 거의 없습니다.
- **함께 발견한 점**: 가벼운 클라이언트에서 짧은 파일부터 보내면 9.7초, 긴 파일부터 보내면 10.3초였습니다.
  README는 `--sort-by-length`(긴 파일부터)를 권하는데, 순서의 영향은 따로 확인해 볼 만합니다.
